# BillLearn MVP 구현 계획 한국어 해설

이 문서는 실행용 영문 구현 계획을 이해하기 쉽게 풀어쓴 한국어 버전입니다.
실제 구현 체크리스트와 코드 블록은 영문 원본 계획인 `2026-05-14-billlearn-mvp-implementation.md`를 기준으로 진행합니다.

## 목표

BillLearn MVP의 첫 구현 목표는 다음 흐름을 실제 앱 구조로 만드는 것입니다.

1. Flutter 앱 프로젝트를 생성합니다.
2. 홈, 내역, 상세, 설정 화면의 기본 구조를 만듭니다.
3. 원본 알림, 거래 후보, 최종 지출, 판정 결과 모델을 분리합니다.
4. 결제 문자와 알림 본문에서 금액, 가맹점, 결제 수단 힌트를 파싱합니다.
5. 중복, 이체성 이벤트, 실제 지출 여부를 규칙 기반으로 판정합니다.
6. Android 알림/SMS 수집 이벤트를 Flutter로 전달하는 브리지를 만듭니다.
7. 수집된 원본을 파싱하고 실제 지출로 저장하는 처리 흐름을 연결합니다.
8. 테스트, 정적 분석, Android debug APK 빌드로 검증합니다.

## 기술 선택

이번 계획에서는 다음 기술을 사용합니다.

- `Flutter`: Android와 iOS 양쪽으로 확장 가능한 공통 앱 UI
- `Dart 3`: Flutter 앱과 도메인 로직
- `Riverpod`: 상태 관리
- `go_router`: 화면 라우팅
- `drift + sqlite`: 향후 로컬 저장소 구현을 위한 SQLite 계층
- `Android Kotlin`: Android 전용 알림/SMS 수집
- `MethodChannel/EventChannel`: Android 네이티브 코드와 Flutter 사이의 연결
- `flutter_test`: 파서, 판정, 저장소, 화면 테스트

## 작업 1: Flutter 프로젝트 생성

`app/` 폴더 안에 Flutter 프로젝트를 만듭니다. 현재 저장소에는 문서만 있으므로, 앱 코드는 문서와 분리해 `app/` 아래에 둡니다.

이 단계에서 `pubspec.yaml`에 필요한 패키지를 추가하고, 기본 테스트가 통과하는지 확인합니다. 현재 폴더가 git 저장소가 아니므로 구현을 시작할 때는 `git init`을 먼저 실행할 수 있습니다.

## 작업 2: 앱 셸, 라우팅, 테마, 네비게이션

BillLearn 앱의 기본 껍데기를 만듭니다.

생성되는 주요 화면은 다음과 같습니다.

- `홈`: 이번 달 실제 지출, 확인 필요 항목, 최근 내역
- `내역`: 날짜별 거래 내역
- `상세`: 특정 거래의 상세 정보
- `설정`: 권한과 데이터 관리

브랜드 색상은 시안에 맞춰 `Main Purple #6C4EFF`, `Light Purple #EDE9FF`, `Soft Gray #F6F7FB`, `White #FFFFFF` 계열을 사용합니다.

## 작업 3: 도메인 모델 추가

앱의 핵심 데이터 구조를 만듭니다.

- `RawNotification`: Android 푸시 알림 또는 SMS 원본
- `TransactionCandidate`: 원본에서 파싱한 결제 후보
- `ExpenseTransaction`: 사용자에게 보여줄 최종 실제 지출
- `ClassificationResult`: 중복, 이체, 실제 지출 여부에 대한 판정 결과

이 분리가 중요합니다. 원본 알림을 바로 지출로 저장하면 중복 결제나 계좌이체를 잘못 계산하기 쉽기 때문입니다.

## 작업 4: 결제 텍스트 파서

한국어 결제 문자나 알림 본문에서 다음 정보를 추출하는 파서를 만듭니다.

- 금액
- 가맹점명
- 결제 수단 힌트
- 원본 수신 시간

첫 버전은 정규식 기반으로 시작합니다. 예를 들어 `[신한카드 승인] 12,300원 스타벅스 05/14 12:30` 같은 텍스트에서 `12300`, `스타벅스`, `신한카드`를 추출합니다.

## 작업 5: 지출 판정기

파싱된 거래 후보를 실제 지출로 볼지 판정하는 규칙을 만듭니다.

초기 규칙은 다음을 다룹니다.

- 같은 금액, 같은 가맹점, 가까운 시간대면 중복 후보로 봅니다.
- `이체`, `입금`, `출금`, `송금`, `충전`, `자동이체`, `계좌간`, `내 계좌` 같은 단어가 있으면 이체성 이벤트로 봅니다.
- 금액과 가맹점이 안정적으로 파싱되고 이체성이 없으면 실제 지출로 확정합니다.
- 애매한 경우는 확인 필요 상태로 남깁니다.

## 작업 6: 저장소 인터페이스와 메모리 구현

UI가 데이터베이스를 직접 알지 않도록 `ExpenseRepository` 인터페이스를 만듭니다.

처음에는 실제 DB 대신 `InMemoryExpenseRepository`를 만들어 테스트와 화면 연결을 빠르게 진행합니다. 이후 `drift` 기반 로컬 DB 구현으로 교체할 수 있습니다.

이 단계의 목적은 나중에 서버 동기화를 붙이더라도 화면과 도메인 로직이 크게 흔들리지 않게 하는 것입니다.

## 작업 7: Android 이벤트 브리지

Android 네이티브 코드에서 발생한 원본 이벤트를 Flutter로 넘기는 통로를 만듭니다.

- `MethodChannel`: 권한 상태 확인, 설정 화면 열기 같은 요청/응답 작업
- `EventChannel`: 알림이나 SMS가 들어왔을 때 Flutter로 이벤트 스트림 전달

Flutter 쪽에서는 Android payload를 `RawNotification` 모델로 변환합니다.

## 작업 8: Android 알림과 SMS 수집기

Android 네이티브 기능을 추가합니다.

- `NotificationListenerService`: 푸시 알림 본문을 읽어 원본 이벤트로 전달
- `BroadcastReceiver`: SMS 수신 이벤트를 읽어 원본 이벤트로 전달
- `AndroidManifest.xml`: 알림 리스너, SMS 권한, SMS receiver 선언

이 단계는 실제 Android 기기 테스트가 중요합니다. 에뮬레이터나 제조사 환경에 따라 알림 접근 권한 흐름이 다르게 보일 수 있습니다.

## 작업 9: 원본 이벤트 처리 파이프라인 연결

수집된 `RawNotification`을 실제 앱 흐름에 연결합니다.

처리 순서는 다음과 같습니다.

1. 원본을 저장합니다.
2. 원본 본문을 `TransactionCandidate`로 파싱합니다.
3. 후보를 `ClassificationResult`로 판정합니다.
4. 실제 지출이면 `ExpenseTransaction`으로 저장합니다.
5. 실제 지출이 아니면 원본만 남기고 홈 내역에는 표시하지 않습니다.

이 단계가 BillLearn의 핵심 제품 흐름입니다.

## 작업 10: 최종 검증

구현이 끝나면 다음 명령으로 검증합니다.

- `dart format lib test`
- `flutter analyze`
- `flutter test`
- `flutter build apk --debug`

모든 검증이 통과하면 Android에서 실행 가능한 MVP 기반이 만들어진 상태입니다.

## 구현 시 주의할 점

- 첫 버전에서 AI 판정은 넣지 않습니다.
- 예산 관리와 소비 인사이트는 MVP에 넣지 않습니다.
- iOS 자동 수집은 MVP 목표가 아닙니다.
- 원본 데이터와 최종 지출 데이터는 반드시 분리합니다.
- Android 권한 안내는 기능 설명보다 신뢰 형성이 중요합니다.
- 나중에 서버 동기화를 붙일 수 있도록 UI가 DB 구현을 직접 알지 않게 합니다.
