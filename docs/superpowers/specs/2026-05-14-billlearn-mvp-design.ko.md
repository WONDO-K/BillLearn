# BillLearn MVP 설계

## 개요

BillLearn은 결제 영수증, 푸시 알림, SMS 메시지로부터 배우는 자동 개인 지출 기록 앱입니다. 첫 제품 타깃은 Android입니다. Android는 사용자의 허가를 받으면 결제 관련 알림과 SMS 메시지를 수집할 수 있기 때문입니다. 다만 제품 구조는 향후 iOS 지원과 MyData, 금융 API 같은 서버 기반 데이터 소스를 붙일 수 있도록 설계합니다.

MVP의 핵심 흐름은 하나입니다.

1. 결제 알림과 SMS 메시지를 수집합니다.
2. 수집한 원본을 거래 후보로 파싱합니다.
3. 중복, 이체, 비지출 이벤트를 판정합니다.
4. 확정된 실제 지출만 저장합니다.
5. 정리된 지출 데이터를 홈과 내역 화면에 보여줍니다.

예산 관리, 고급 분석, AI 인사이트 기능은 MVP 범위에서 제외합니다. 자동 수집과 실제 지출 정리 흐름이 충분히 신뢰할 수 있게 된 뒤 추가합니다.

## 제품 원칙

- BillLearn은 단순 알림 수집기가 아니라 지출 정리 시스템처럼 동작해야 합니다.
- 원본 알림 데이터와 최종 지출 데이터는 분리해야 합니다.
- 홈과 내역 화면에는 정리된 실제 지출만 보여줘야 합니다.
- 애매한 케이스는 사용자에게 보이고 쉽게 수정할 수 있어야 합니다.
- 앱은 회원가입 없이 시작할 수 있어야 합니다.
- MVP는 로컬 저장을 기본으로 하되, 모델은 향후 서버 동기화를 붙일 수 있어야 합니다.

## 플랫폼 전략

MVP는 Flutter로 공통 앱 UI와 도메인 로직을 만들고, Android 전용 수집 기능은 네이티브 모듈로 분리합니다.

Flutter가 담당하는 영역은 다음과 같습니다.

- 앱 화면과 네비게이션
- 공통 도메인 모델
- 지출 판정 결과 표시
- 로컬 저장소 인터페이스
- 홈, 내역, 상세, 설정 흐름

Android 네이티브 코드가 담당하는 영역은 다음과 같습니다.

- `NotificationListenerService`를 통한 알림 접근
- SMS 권한과 SMS 수집
- Android 권한 상태 확인
- MethodChannel 또는 EventChannel을 통한 Flutter 브리지 연동

iOS는 MVP에서 자동 수집의 1차 대상이 아닙니다. iOS는 Android처럼 알림과 SMS에 폭넓게 접근하는 구조를 제공하지 않기 때문입니다. 향후 iOS 지원은 Flutter UI와 도메인 개념을 재사용하되, MyData, 카드사 연동, 금융 API, 서버 동기화, 수동 입력 같은 다른 입력원을 통해 데이터를 받는 방향으로 설계합니다.

## MVP 화면

### 홈

홈 화면은 이번 달 실제 지출, 최근 정리된 거래, 사용자 확인이 필요한 항목 요약을 보여줍니다. 화이트와 퍼플 중심의 BillLearn 브랜드 방향을 반영하고, 마스코트는 신뢰감을 보조하는 정도로 선택적으로 사용합니다.

### 내역

내역 화면은 실제 지출을 날짜별로 묶어서 보여줍니다. 기간과 카테고리 기준의 간단한 필터를 지원합니다. 이 화면은 원본 알림이 아니라 확정된 `ExpenseTransaction` 데이터를 읽습니다.

### 거래 상세

거래 상세 화면은 최종 거래 정보, 연결된 원본 정보, 판정 근거, 카테고리, 사용자 피드백 액션을 보여줍니다. 사용자는 이 화면에서 앱이 거래를 제대로 해석했는지 확인하고 수정할 수 있습니다.

### 설정과 권한

설정 화면은 알림 접근 상태, SMS 권한 상태, 로컬 데이터 관리, 향후 계정/동기화 진입점을 보여줍니다. Android 알림 접근 권한은 시스템 설정 화면에서 켜야 하므로, 권한 복구 흐름이 명확해야 합니다.

## 온보딩

첫 실행 경험은 앱의 목적을 직접적이고 개인정보 관점에서 납득 가능하게 설명해야 합니다.

> BillLearn은 결제 알림과 SMS 메시지에서 금액, 가맹점, 시간을 읽어 실제 지출만 정리합니다. 원본 데이터는 먼저 이 기기에 저장됩니다.

온보딩은 모든 권한을 한 번에 요구하지 않습니다. 알림 접근과 SMS 접근의 목적을 각각 설명합니다.

- 알림 접근: 카드사, 은행, 결제 앱의 푸시 알림을 분석하는 데 사용합니다.
- SMS 접근: 카드사와 은행의 결제 문자 메시지를 분석하는 데 사용합니다.

사용자는 회원가입 없이 시작할 수 있습니다. 권한을 허용하지 않은 경우 샘플 데이터나 제한된 빈 상태를 보여줄 수 있지만, 자동 수집에는 Android 권한이 필요하다는 점을 분명히 안내해야 합니다.

## 도메인 모델

### RawNotification

`RawNotification`은 Android 푸시 알림 또는 SMS 메시지에서 들어온 원본 입력입니다.

필드:

- `id`
- `sourceType`
- `sourceApp`
- `sender`
- `title`
- `body`
- `receivedAt`
- `sourceHash`
- `createdAt`

원본 데이터는 파싱, 중복 판정, 사용자 수정의 근거로 보관합니다.

### TransactionCandidate

`TransactionCandidate`는 원본 입력에서 추출한 결제성 이벤트입니다. 아직 확정된 지출은 아닙니다.

필드:

- `id`
- `rawNotificationId`
- `amount`
- `merchantName`
- `paymentMethodHint`
- `occurredAt`
- `sourceType`
- `parseConfidence`
- `parseStatus`
- `createdAt`

### ExpenseTransaction

`ExpenseTransaction`은 사용자에게 보여줄 최종 지출 거래입니다.

필드:

- `id`
- `amount`
- `merchantName`
- `categoryId`
- `spentAt`
- `confirmationStatus`
- `confirmedBy`
- `candidateIds`
- `createdAt`
- `updatedAt`
- `syncStatus`

### ClassificationResult

`ClassificationResult`는 후보 또는 후보 그룹에 대해 내려진 판정 결과입니다.

필드:

- `id`
- `candidateIds`
- `isDuplicate`
- `isTransferLike`
- `isExpense`
- `requiresReview`
- `reasonCodes`
- `confidence`
- `createdAt`
- `userFeedback`

## 판정 규칙

MVP는 설명 가능한 규칙 기반 판정으로 시작합니다. AI는 충분한 예시와 수정 데이터가 쌓인 뒤 추가할 수 있습니다.

### 중복 판정

후보들은 다음 조건이 맞으면 같은 거래로 묶습니다.

- 금액이 같거나 매우 비슷합니다.
- 가맹점명이 유사합니다.
- 시간이 가깝습니다.
- 결제 수단 또는 계좌/카드 힌트가 일치합니다.

이 규칙은 카드 푸시 알림과 SMS 메시지가 같은 결제를 동시에 설명하는 일반적인 상황을 처리합니다.

### 이체와 비지출 판정

본문에 다음과 같은 이체성 패턴이 있으면 실지출 우선순위를 낮추거나 확인 필요 상태로 보냅니다.

- `이체`
- `입금`
- `출금`
- `송금`
- `충전`
- `자동이체`
- `계좌간`
- `내 계좌`

자동이체는 무조건 제외하지 않습니다. 통신비, 보험료, 구독, 공과금 같은 실제 지출도 자동이체 형태로 나타날 수 있기 때문입니다. 애매한 케이스는 조용히 제거하지 않고 확인 필요 항목으로 보냅니다.

### 실제 지출 확정

카드 승인, 체크카드 결제, 결제 앱 승인처럼 결제 문구가 안정적이고 금액, 가맹점, 시간 신호가 충분하면 지출로 확정할 수 있습니다.

### 확인 필요

다음 경우 후보는 확인 필요 상태가 됩니다.

- 금액은 있지만 가맹점 파싱이 약합니다.
- 이체 신호와 지출 신호가 동시에 있습니다.
- 중복 가능성이 높지만 확정적이지 않습니다.
- 원본 텍스트가 아직 지원되지 않거나 익숙하지 않은 형식입니다.

### 피드백 학습

사용자 수정은 구조화된 피드백으로 저장합니다. 반복 피드백은 발신자 패턴 제외나 특정 가맹점 카테고리 적용 같은 로컬 규칙으로 발전시킬 수 있습니다.

## 데이터와 동기화 전략

MVP는 로컬 우선입니다. 데이터는 필수 계정 생성 없이 기기에 저장합니다.

다만 향후 동기화를 준비하기 위해 다음을 지킵니다.

- UI가 데이터베이스에 직접 접근하지 않고 저장소 인터페이스를 사용합니다.
- 안정적인 ID와 타임스탬프를 유지합니다.
- 사용자에게 보이는 레코드에는 `syncStatus`를 저장합니다.
- 도메인 판정 규칙 안에 데이터베이스 전용 로직을 넣지 않습니다.
- 원본 입력, 후보, 판정 결과, 최종 지출을 분리합니다.

향후 서버 동기화는 기존 저장소 인터페이스 뒤에 다른 구현체나 동기화 계층으로 추가할 수 있습니다.

## 아키텍처

Flutter 프로젝트는 네 가지 주요 영역으로 구성합니다.

### Presentation

화면, 네비게이션, 상태 관리, 시각 컴포넌트를 포함합니다. Presentation 코드는 유스케이스나 저장소를 통해 데이터를 요청하며 Android 알림이나 SMS 구현 세부사항을 알지 않습니다.

### Domain

핵심 모델, 판정 로직, 중복 그룹화, 이체 감지, 유스케이스 인터페이스를 포함합니다. 이 계층은 Flutter UI나 Android 런타임 의존성 없이 테스트할 수 있어야 합니다.

### Data

로컬 데이터베이스 구현, 파서, 저장소 구현체, 동기화 대비 영속화 필드를 포함합니다. MVP 저장소는 SQLite 계열의 Flutter 친화적인 로컬 데이터베이스를 사용할 수 있습니다.

### Platform Android

Android 전용 수집기와 브리지 코드를 포함합니다. 이 계층은 원본 알림과 SMS 이벤트를 안정적인 계약을 통해 Flutter로 전달합니다.

## 테스트 전략

### 파서 테스트

대표적인 결제 알림과 SMS 메시지에서 금액, 가맹점, 시간, 출처 필드가 정확히 추출되는지 검증합니다.

### 판정 테스트

푸시 알림과 SMS 중복 케이스, 이체성 케이스, 자동이체 애매 케이스, 결제 앱 승인, 미지원 텍스트를 검증합니다.

### 저장소 테스트

원본 입력, 후보, 판정 결과, 최종 지출이 분리 저장되고 서로 연결될 수 있는지 검증합니다.

### UI 테스트

홈과 내역 화면이 `ExpenseTransaction` 데이터만 보여주고, 확인 필요 항목이 명확히 분리되는지 검증합니다.
